An insight here means: a measured pattern, plus the decision it informs, plus the action to take. The patterns come first; the cases, coverage, and project tables that support them follow. Nothing here is a single anecdote dressed up as a trend.

My assessment

You get useful implementation work from AI. The weak point is reliable completion. In the inspected cases, agents can produce code, recover from test failures, and make focused changes. They struggle more when correctness crosses a browser, an API, a database, or an unfamiliar framework contract.

Your direct feedback helps. It also means you sometimes become the integration test: “where is the chat interface?”, “again i got problem”, or a browser error arrives after a successful build. A clearer acceptance check would catch some of that work before it reaches you.

The change I would make first: give each task one observable result, then require evidence that it works. Keep the fast prototyping. Tighten the finish. A build, a green shell status, and an agent's final summary are three different kinds of evidence.

P1 · Short prompts cost more than long ones Prompt habit

Sessions that open with under 200 characters settle at a median of 566k token traffic, 23 tool calls, and 3 user messages. Sessions that open with 2,000+ characters settle at 388k traffic, 12 tool calls, and 1 user message. The detailed brief costs roughly a third less traffic and half the tool calls, with a third of the follow-ups.

59% of all your user messages (1,342 of 2,275) are under 100 characters. Brevity at the start is paid back with interest in corrections.

Do this: open coding tasks with 200+ characters covering goal, scope, and acceptance check. Watch: median tool calls per session for well-briefed tasks vs. the rest.

P2 · Correction loops concentrate the spend Loop control

73 sessions (9%) with 8 or more user messages account for 43.8% of all recorded traffic. The typical session has 1 user message and 11 assistant records; the heavy tail is where the tokens go. This is not “AI is expensive.” It is “unfinished tasks are expensive.” The twelve heaviest loop sessions read like the family table in the Work section: data viewers, upload features, video-call fixes, localhost debugging.

Do this: after two failures with the same cause, stop the thread. Restate the failed assumption, shrink the goal, or restart with a handoff (accepted behavior, relevant paths, failing check, next step). Watch: traffic share from sessions with 8+ user messages — drive it down from 43.8%.

P3 · “Continue” is the most expensive word Prompt habit

“Continue” is your second most common message opening (157 times, after “you”). 107 sessions contain a bare continue-nudge, and they hold 42% of total traffic (761M of 1.81B). A nudge keeps every alternative alive in context instead of selecting one. It is the linguistic form of the correction loop in P2. Image-bearing messages (58) cluster in the same loops: pictures arrive after words failed.

Do this: replace “continue” with a decision: what to keep, what to change, and what done looks like. If there is nothing new to say, the previous instruction was incomplete — rewrite it instead of nudging. Watch: bare continue-nudges per ten tasks.

P4 · Reads are small, blind, and often truncated Context hygiene

Reads are your top tool (11,044 calls, 42.75M returned characters, 48% of all tool-result text). Only 8% use an offset and 14% a limit — the default is the whole file. One in ten reads (1,171) comes back truncated: context paid for text nobody can use. Exact duplicate re-reads are only 3.6% of read-family calls (495 of 13,618), so the waste is not repetition — it is oversized first reads. Meanwhile 6,691 assistant records with 100k+ context tokens carry 57.5% of all traffic, and records over 200k carry 15.0%. Cache reuse is cheap; the cost is attention spread over stale observations.

Do this: symbol search first (grep/glob), then read the function and its callers with offset/limit. Extract fields from large schemas and logs instead of reading them whole. Split the conversation when the deliverable changes, carrying a short handoff. Watch: truncated-read rate — drive it down from 10.6%.

P5 · Edits fail on stale text, then fail the same way again Edit discipline

210 of 4,241 edit calls error; 172 of those (81.9%) cannot find the old string — the agent edited from memory or from a file that already changed. 22 sessions hit this same error three or more times. The retry almost never works because the premise, not the formatting, is wrong.

Do this: after one old-string mismatch, re-read the exact block and shrink the patch. Never retry the same replacement twice. Put that sentence in your coding prompt. Watch: edit error rate (now 5.0%) and sessions with 3+ stale-edit errors (now 22).

P6 · A third of edits get no matching check Verification

105 of 350 editing sessions (30%) have no test/build/lint/check command and no render or network probe of any kind. The check is not missing because the work is trivial — the heaviest families include long editing sessions with no recorded verification. Passing builds elsewhere in the history coexist with broken browser behavior (E03, E07), so “it compiled” is the weakest claim that still feels like proof.

Do this: match the check to the claim — type check for types, behavioral test for state rules, screenshot for UI, two clients for isolation. Require the check name and result in the closing message. Watch: edit sessions with zero verification — drive down from 30%.

P7 · Piped checks hide failures Verification

1,421 check-like shell commands pipe through tail, head, rg, or grep with no pipefail or PIPESTATUS. The recorded exit then belongs to the filter, not the test. One observed run reported exit 0 alongside “8 pass, 4 fail” (E02). The agent in that case read the output anyway — the danger is the runs where nobody reads it.

Do this: run checks unpiped; when a pipeline is needed, set pipefail. Read the summary line, not just the exit code. Watch: piped-check count when reviewing diffs.

P8 · Agents retry dead capabilities instead of switching tools Tool use

All 4 vision calls errored (oversize image, unreachable endpoint, wrong file types). All 7 browser-control status probes returned “Unknown tool” — one session tried six name variants of a tool that does not exist. Web fetching fails at 12.9% (122 of 946), led by raw.githubusercontent.com (27) and opencode.ai (24): guessed raw-file URLs and versioned docs that 404 or arrive too large (173 webfetch outputs exceed 20k chars). Meanwhile the shell-based fallback worked every time it was tried: 96 screenshot commands and 530 curl probes across the window. The pattern is persistence in the wrong direction — when a capability is missing, agents rephrase the call instead of changing the approach.

Do this: one capability error means switch tools, not retry. Prefer shell-executed rendering (firefox --headless --screenshot) and curl probes; pin fetched docs to the installed version and extract instead of dumping pages into context. Watch: any second consecutive call to a tool that just errored “unknown” or “unsupported.”

P9 · Delegation works when subtasks are verified, not trusted Supervision

295 delegation calls produced 38 errors and 16 empty child sessions (5% of children). The failures that hurt are silent ones: a worker reporting “all checks pass” on zero executed tests (E06), or parallel writers shipping into a tree that never built. The recoveries that worked share one shape — the parent re-ran the check itself and sent the work back with a specific correction. The question tool (136 calls across 91 sessions) shows agents do ask; the gap is that short vague briefs plus few upfront questions produce the loops in P2. Verification at the integration point is the whole technique.

Do this: give editing agents disjoint file sets, keep one integration owner, and re-run every subtask's check yourself before accepting it. Never accept a self-report as evidence. Instruct agents to ask 1–3 blocking questions before implementing (the E08 deletion did exactly this). Watch: empty-child count (now 16) and rework rounds per delegation.

P10 · The shell is now the whole workshop Tool mix

The bash tool carried July (1,922 calls); the shell tool carries August onward (5,163 in August, 2,576 in September against 5 bash calls). Python-inside-shell rose with it to 10.6% of September shell calls — agents reach for Python to probe, parse, and analyze. The workshop consolidated onto one tool and the agents adapted within weeks. Two hygiene issues ride along: probe scripts (dbg.ts) get created inside repos instead of /tmp (seen in E01), and a few huge outputs dominate the noise (104 shell outputs exceed 20k chars). Browser automation is the expensive corner of shell use: Playwright click retries burn 8–30 seconds per attempt inside the framework's own visibility loop, and one silent null with exit 0 cost more than any loud failure. Timeout exits (124) appear 18 times across 11 sessions.

Do this: keep Python for analysis tasks; require scratch files to live in /tmp/opencode and be deleted after use. Watch: stray dbg.* / probe.* files left in repos — target zero.

Evidence cases E01–E08

Each case separates an attempted edit, a real failure, and a verified recovery. Historical evidence describes the code at that point, not the current state of a moved repository. Tool numbers refer to the normalized review database; message IDs refer to the recorded history.

E01 · Tests recovered the implementation after guessed TypeScript APIs failed Verified recovery

The agent called ts.isTupleType(ref), which raised “is not a function.” A debugging probe then called checker.getProgram(), which also failed. Loop handling used stmt.body, but the inspected node had statement. These are concrete API-shape errors, not style concerns.

The good part is the recovery. The agent inspected actual node keys, corrected the loop property, and reached 19 passing tests. A later production build completed. Some test expectations also changed, so a green suite still needs a diff review.

Change: inspect the installed type declarations or a minimal runtime probe before implementing unfamiliar compiler APIs. Keep semantic tests. Review changed assertions separately from implementation changes.

The same session ran a production build through tail. The output said the build failed, but the shell metadata again reported zero. The filter's exit status hid the original failure. The agent read the output and kept fixing it, so this is not a claim that it declared those runs successful.

Change: run checks directly; preserve the original exit status (set -o pipefail). Read the test summary as well as the exit code.

E03 · The chat compiled, but the browser path did not work Integration failure

The original chat client used a browser request to NVIDIA and documented VITE_NVIDIA_API_KEY. A build passed. Follow-up sessions still contained “why is the ai chat not working” and the browser's explicit CORS failure. A later environment value overrode the intended Vite proxy path.

Direct API requests returned HTTP 200 during debugging, but that did not prove the browser flow worked. Provider availability, browser CORS, configuration precedence, and response parsing were separate problems.

Quality concern: a provider secret supplied through a VITE_ variable belongs to the client bundle. A development proxy alone does not make that a server-owned credential. This is evidence of a risky historical design, not proof that a production key leaked.

Change: keep the provider request and credential on a server route. Test the actual browser-to-server-to-provider flow. Check the effective request URL before adding retries.

E04 · A confident reviewer applied the wrong Tailwind rule Bad review

A review flagged sm:h-13 as invalid because the default scale supposedly jumps from 12 to 14. That reasoning is wrong for Tailwind 4: numeric height utilities use calc(var(--spacing) * number). The historical stylesheet uses the v4 @theme format, and a retained package read declares Tailwind ^4.

The review also suggested a server route could choose a favicon from the saved theme while describing that theme as stored in localStorage. That needs an explicit way to send the preference to the server. It is not a complete fix as written.

Change: require a reproduction or version-matched reference for a framework-specific review finding. A severity label is not evidence. AI review can create unnecessary fixes as well as find real defects.

The favicon task created the icon assets, ran type checking, and built the app. A scoped check found a missing SVG accessibility title. The agent fixed it, then the scoped check passed. The build listed the icon routes.

E06 · A subagent reported passing tests that never ran Caught by supervision

The API worker wrote search checks with top-level assertions instead of registered tests. Its run printed [search] all checks passed with 0 pass, 0 fail, and its report still claimed the live-database section passed. The parent reproduced the same 0 pass / 0 fail output and sent the work back with an explicit instruction to register real tests. After rework, the file reported 14 pass / 0 fail, including a deep-typo fuzzy search test against Postgres.

Change: treat a subagent's self-report as a claim, not evidence. Re-run the check at the integration point. A runner that reports zero tests has verified nothing.

E07 · One costly visual session never rendered the page; a cheaper one did Missing verification

The /minimal checking session used 27 user messages, 226 tools, 102 edits, and 38.44M traffic. Its corrections were visual: spacing, edges, overlapping images, broken scroll, fonts. The session contains no screenshot, browser, Playwright, or curl tool call. The scroll break traces to the agent's own CSS edit that removed two overflow properties; the user found it and a later commit message names the cause. The agent's text answer to “does this look the same?” was honest (“close in spacing, not the same”), but honesty is not a substitute for rendering.

In the same window, the gptmap parent captured headless Firefox screenshots of the app and a reference page, re-rendered after changes, and sent both images to the follow-up worker. Visual claims need pixels, not another build.

Change: for visual tasks, capture a screenshot before and after the change. Send the reference image with the correction. Do not count compiles or lint as visual verification.

E08 · A 39-character delete request got confirmation, reference checks, and honest verification Careful execution

Asked to “delete all styles and ui and and pages,” the agent confirmed scope with graded options before deleting, checked for dangling asset references, and committed a +8 / −719 change. Do not treat every redesign as waste. Exploring alternatives, changing your mind, or learning a framework can be the point. Count a preference change separately from a missed requirement. A missing old path does not prove work was discarded.

Do not choose a model from these totals alone. The history contains 44 provider/model routes with different tasks, contexts, and tools. It is not a controlled benchmark. Zero recorded cost says nothing about how much of your attention a task required.

Changes I would make

  1. Define one acceptance result. State the behavior you will observe. Include the failure state when it matters.
  2. Inspect the integration contract first. Identify the request, response, authorization rule, state owner, and installed version. For real-time features, add disconnect and reconnect behavior.
  3. Use a two-failure stop rule. After two failures with the same cause, stop editing. State the failed assumption. Run a check that distinguishes the next hypothesis. Expected red tests are not retry waste.
  4. Match the check to the claim. A type check tests types. A browser check tests interactions. Two authenticated clients can test isolation or real-time delivery. Preserve test exit status.
  5. Constrain design exploration. Pick a representative screen and a reference. Specify density, navigation, typography, and important interactions. Review it before rewriting every page.
  6. Delegate bounded work. Use free models for repository maps and independent read-only checks. Give editing agents distinct files. Keep one owner for the combined diff and acceptance test.
  7. Start a new conversation when the goal changes. Carry forward the accepted result, relevant paths, unresolved issue, and next step.
  8. Close with evidence. Ask for the check, result, remaining gap, and relevant diff. If a prerequisite blocks verification, keep that distinction visible.
A reusable prompt for a coding task 
Goal: [one observable user behavior]
Scope: [project and relevant files]
Acceptance: [the check that proves the behavior]
Constraints: [versions, existing server, data boundaries]

Inspect the current implementation before editing.
Use the installed API and version-matched documentation.
If the same failure occurs twice, identify the failed assumption.
Run a different diagnostic before another edit.
Preserve the original exit status of checks.
Finish with the changed behavior, check results, and remaining gap.
Use free OpenCode models for any delegated work.

For model choice, start with a free model on a bounded task. Escalate a persistent reasoning problem or important review to a stronger model or your own inspection. Do not switch repeatedly without naming what the next model must resolve.

P11 · Agents write POSIX for a fish shell Environment

The shell tool runs fish. Agents write VAR=value assignments and POSIX redirections anyway: 28 “Unsupported use of '='” errors across 22 sessions and 25 redirection errors across 18 sessions — 53 failed calls in 34 distinct sessions, all projects mixed. Exit 127 accounts for 174 of the 748 nonzero shell exits. The same CHUNK=$(curl …) command failed twice in a row in one session. Nobody tells the agent which shell it got, so it guesses the default and keeps guessing.

Do this: state the shell in the project instructions (fish) with two examples (set VAR value, no VAR=x, no <()). Better: add a shell-dialect line to the agent prompt once, globally. Watch: exit-127 rate and fish-dialect errors — 53 calls is the baseline to beat.

Method and limits

Read-only snapshots of opencode.db and opencode-next.db via the SQLite backup API; newer message schema preferred, 528 duplicate IDs and 360 fork-copied responses removed, 476 legacy messages recovered. Aggregates cover all 26,021 normalized messages; cohort medians (P1) are observational. Token traffic is defined as input + output + cache reads + cache writes; the $46.38 cost field is a record, not a bill.

Three free-model reviewers were assigned separate project groups, but their tools could not query the normalized database — one failed outright in a repetition loop and produced nothing. Summary-only claims were treated as leads throughout. Every case above relies only on transcript, tool-output, or source evidence re-checked by hand.

  • This is a review of recorded work, not a fresh test run or security audit of every repository.
  • Current files can differ from historical generated code. Moved paths do not prove deletion.
  • Deleted history, work outside OpenCode, and missing provider usage are not visible.
  • Tool completion does not establish command success. A build does not establish working user behavior.
  • Check detection is a broad command-text heuristic. It can miss real checks and match commands that only mention them.
  • Token fields vary by provider. Traffic is explicitly defined here and is not an invoice or fresh-content count.
  • Tool duration can include idle time. Concurrent calls prevent simple time summation.
  • The qualitative sample is targeted. It cannot establish a defect percentage or a fair model ranking.
  • Some sessions were still open at the snapshot boundary.
