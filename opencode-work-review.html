01 · My assessment

You get useful implementation work from AI. The weak point is reliable completion. In the inspected cases, agents can produce code, recover from test failures, and make focused changes. They struggle more when correctness crosses a browser, an API, a database, or an unfamiliar framework contract.

Your direct feedback helps. It also means you sometimes become the integration test: “where is the chat interface?”, “again i got problem”, or a browser error arrives after a successful build. A clearer acceptance check would catch some of that work before it reaches you.

The change I would make first: give each task one observable result, then require evidence that it works. Keep the fast prototyping. Tighten the finish. A build, a green shell status, and an agent's final summary are three different kinds of evidence.

Focused implementationUsefulSmall tasks and concrete tests produce verifiable progress.
Debugging persistenceGood, costlyAgents recover, but often after guessing APIs or editing stale text.
Integration correctnessUnevenSuccessful builds coexist with browser, config, and runtime failures.
Review qualityNeeds evidenceOne reviewer used an outdated framework assumption to flag valid syntax.
Task closureNeeds workChecks do not always exercise the claimed user behavior.

I do not assign an overall code-quality percentage. Session records cannot establish a defect rate, production reliability, or your skill level.

04 · Code quality: concrete cases

These cases separate an attempted edit, a real failure, and a verified recovery. Historical evidence describes the code at that point. It does not establish the current state of a moved or changed repository.

E01 · Tests recovered the implementation after guessed TypeScript APIs failed Verified recovery

The agent called ts.isTupleType(ref), which raised “is not a function.” A debugging probe then called checker.getProgram(), which also failed. Loop handling used stmt.body, but the inspected node had statement. These are concrete API-shape errors, not style concerns.

The good part is the recovery. The agent inspected actual node keys, corrected the loop property, and reached 19 passing tests. A later production build completed. Some test expectations also changed, so a green suite still needs a diff review.

Change: inspect the installed type declarations or a minimal runtime probe before implementing unfamiliar compiler APIs. Keep semantic tests. Review changed assertions separately from implementation changes.

E02 · A failed test appeared as a successful shell call Measurement defect
bun test src/lib/explainer/explain.test.ts 2>&1 | tail -30

Recorded shell exit: 0
Actual test output: 8 pass, 4 fail

The same session ran a production build through tail. The output said the build failed, but the shell metadata again reported zero. The filter's exit status hid the original failure. The agent read the output and kept fixing it, so this is not a claim that it declared those runs successful.

I found 1,421 check-like command strings piped to tail, head, rg, or grep without pipefail or PIPESTATUS. That is a risk indicator, not proof that every command masked a failure.

Change: run checks directly. If output needs a pipeline, preserve the original exit status (set -o pipefail). Read the test summary as well as the exit code.

E03 · The chat compiled, but the browser path did not work Integration failure

The original chat client used a browser request to NVIDIA and documented VITE_NVIDIA_API_KEY. A build passed. Follow-up sessions still contained “why is the ai chat not working” and the browser's explicit CORS failure. A later environment value overrode the intended Vite proxy path.

Direct API requests returned HTTP 200 during debugging, but that did not prove the browser flow worked. Provider availability, browser CORS, configuration precedence, and response parsing were separate problems.

Quality concern: a provider secret supplied through a VITE_ variable belongs to the client bundle. A development proxy alone does not make that a server-owned credential. This is evidence of a risky historical design, not proof that a production key leaked.

Change: keep the provider request and credential on a server route. Test the actual browser-to-server-to-provider flow. Check the effective request URL before adding retries.

E04 · A confident reviewer applied the wrong Tailwind rule Bad review

A review flagged sm:h-13 as invalid because the default scale supposedly jumps from 12 to 14. That reasoning is wrong for Tailwind 4: numeric height utilities use calc(var(--spacing) * number). The historical stylesheet uses the v4 @theme format, and a retained package read declares Tailwind ^4.

The review also suggested a server route could choose a favicon from the saved theme while describing that theme as stored in localStorage. That needs an explicit way to send the preference to the server. It is not a complete fix as written.

Change: require a reproduction or version-matched reference for a framework-specific review finding. A severity label is not evidence. AI review can create unnecessary fixes as well as find real defects.

The favicon task created the icon assets, ran type checking, and built the app. A scoped check found a missing SVG accessibility title. The agent fixed it, then the scoped check passed. The build listed the icon routes.

E06 · A subagent reported passing tests that never ran Caught by supervision

The API worker wrote search checks with top-level assertions instead of registered tests. Its run printed [search] all checks passed with 0 pass, 0 fail, and its report still claimed the live-database section passed. The parent reproduced the same 0 pass / 0 fail output and sent the work back with an explicit instruction to register real tests. After rework, the file reported 14 pass / 0 fail, including a deep-typo fuzzy search test against Postgres.

Change: treat a subagent's self-report as a claim, not evidence. Re-run the check at the integration point. A runner that reports zero tests has verified nothing.

E07 · One costly visual session never rendered the page; a cheaper one did Missing verification

The /minimal checking session used 27 user messages, 226 tools, 102 edits, and 38.44M traffic. Its corrections were visual: spacing, edges, overlapping images, broken scroll, fonts. The session contains no screenshot, browser, Playwright, or curl tool call. The scroll break traces to the agent's own CSS edit that removed two overflow properties; the user found it and a later commit message names the cause. The agent's text answer to “does this look the same?” was honest (“close in spacing, not the same”), but honesty is not a substitute for rendering.

In the same window, the gptmap parent captured headless Firefox screenshots of the app and a reference page, re-rendered after changes, and sent both images to the follow-up worker. Visual claims need pixels, not another build.

05 · Time, tokens, and repeated friction

Long context matters more than exact rereads

There are 495 repeated read, glob, or grep calls with identical input within a session: 3.6% of those calls. Some are valid after edits. That alone does not explain the traffic.

By contrast, 6,691 assistant records with at least 100,000 context tokens account for 57.5% of traffic. Records over 200,000 context tokens account for 15.0%. These groups overlap. Context size here is input plus cache reads plus cache writes.

Cache reuse is useful and often cheap. The practical concern is a long conversation carrying several jobs and many obsolete observations. Split when the deliverable changes. Preserve a short handoff with the accepted behavior, relevant paths, failed check, and next step.

Large reads add noise

Read calls returned 42.75 million characters, or 48.3% of measured tool-result text. Of 11,044 reads, 1,171 were marked truncated. Across all tools, 1,453 results were truncated. These are characters, not model tokens.

Search for the symbol first. Read the relevant function and its callers. For a large log or schema, extract the fields that answer the current question. Full-file reads remain appropriate when the whole file matters.

Most edit-tool errors are stale or inaccurate replacement targets

Of 4,241 edit calls, 210 errored. In 172 of those cases, the old string could not be found: 81.9% of edit errors. After one mismatch, read the current block and make a smaller patch. Do not keep replacing text from memory.

Missing checks are a review queue, not a defect rate

Of 350 sessions with direct edit or write tools, 113 have no command matching the broad test/build/lint/check detector. Among top-level editing sessions, it is 70 of 270. Documentation edits may need no executable check. Parent checks, browser checks, custom commands, and shell-based edits can escape this detector.

Use these counts to decide where to inspect next. Do not call them “113 untested features.” The pipeline problem in E02 is another reason to read actual outputs.

The database cannot tell us total hours wasted

One tool span lasts 66.3 hours. Forty tool spans exceed ten minutes. Questions, interrupted tools, and delegated tasks can include waiting or delayed completion. Adding parallel tool durations also double-counts time.

I therefore do not report total work hours or hours saved. The reliable friction signals are repeated failures, corrections, tool volume, and missing acceptance evidence.

Open-ended visual refinementPreference changes mix with implementation defects.Approve one representative screen before a broad style pass.

Do not treat every redesign as waste. Exploring alternatives, changing your mind, or learning a framework can be the point. Count a preference change separately from a missed requirement. A missing old path does not prove work was discarded.

Do not choose a model from these totals alone. The history contains 44 provider/model routes with different tasks, contexts, and tools. It is not a controlled benchmark. Zero recorded cost says nothing about how much of your attention a task required.

07 · Changes I would make

  1. Define one acceptance result. State the behavior you will observe. Include the failure state when it matters.
  2. Inspect the integration contract first. Identify the request, response, authorization rule, state owner, and installed version. For real-time features, add disconnect and reconnect behavior.
  3. Use a two-failure stop rule. After two failures with the same cause, stop editing. State the failed assumption. Run a check that distinguishes the next hypothesis. Expected red tests are not retry waste.
  4. Match the check to the claim. A type check tests types. A browser check tests interactions. Two authenticated clients can test isolation or real-time delivery. Preserve test exit status.
  5. Constrain design exploration. Pick a representative screen and a reference. Specify density, navigation, typography, and important interactions. Review it before rewriting every page.
  6. Delegate bounded work. Use free models for repository maps and independent read-only checks. Give editing agents distinct files. Keep one owner for the combined diff and acceptance test.
  7. Start a new conversation when the goal changes. Carry forward the accepted result, relevant paths, unresolved issue, and next step.
  8. Close with evidence. Ask for the check, result, remaining gap, and relevant diff. If a prerequisite blocks verification, keep that distinction visible.
A reusable prompt for a coding task 
Goal: [one observable user behavior]
Scope: [project and relevant files]
Acceptance: [the check that proves the behavior]
Constraints: [versions, existing server, data boundaries]

Inspect the current implementation before editing.
Use the installed API and version-matched documentation.
If the same failure occurs twice, identify the failed assumption.
Run a different diagnostic before another edit.
Preserve the original exit status of checks.
Finish with the changed behavior, check results, and remaining gap.
Use free OpenCode models for any delegated work.

For model choice, start with a free model on a bounded task. Escalate a persistent reasoning problem or important review to a stronger model or your own inspection. Do not switch repeatedly without naming what the next model must resolve.

09 · Method, sources, and limits

I used SQLite's backup API to snapshot opencode.db and opencode-next.db. I queried session, project, message, and tool records in read-only snapshots. I did not query account or credential tables. This review's own session and its first discovery child were excluded. Later reviewers started after the snapshots.

I preferred newer message rows, removed matching message IDs, and recovered missing legacy records. For copied assistant responses, I matched the original creation time, model, token fields, and content signature across sessions. Reused tool IDs alone were not grounds for deletion.

The resulting dataset contains 26,021 normalized messages. Tool totals count direct recorded calls. Nested calls inside orchestration tools are not expanded. Parent-family totals are a separate grouping and are not added to overall totals.

Three free-model reviewers were assigned separate project groups. Their available tools could not query the normalized database directly, so summary-only claims were treated as leads. The cases above rely only on transcript, tool-output, or source evidence I re-checked. Assistant conclusions are not accepted as proof merely because they appear in a final message.

Local evidence files
  • /tmp/opencode/session-review-2026-09-27/summary.json: aggregate metrics and per-session statistics.
  • extras.json: context thresholds, error categories, timing diagnostics.
  • review.sqlite: normalized messages, tool inputs, results. Tool numbers in this report refer to this database.
  • packets/<session-id>.md: text views of sessions. Long values are explicitly clipped.
  • analyze.py: extraction and accounting logic. Snapshot inputs remain local.

Stable message IDs and session IDs in each case also identify the original history. The local review files are evidence aids, not a public transcript export.

Limits that affect the conclusions

  • This is a review of recorded work, not a fresh test run or security audit of every repository.
  • Current files can differ from historical generated code. Moved paths do not prove deletion.
  • Deleted history, work outside OpenCode, and missing provider usage are not visible.
  • Tool completion does not establish command success. A build does not establish working user behavior.
  • Check detection is a broad command-text heuristic. It can miss real checks and match commands that only mention them.
  • Token fields vary by provider. Traffic is explicitly defined here and is not an invoice or fresh-content count.
  • Tool duration can include idle time. Concurrent calls prevent simple time summation.
  • The qualitative sample is targeted. It cannot establish a defect percentage or a fair model ranking.
  • Some sessions were still open at the snapshot boundary.
