01 · How to read this

This is a learning document, not a status report. I analyzed my own six months of AI-assisted work and turned the findings into rules an engineer can apply. Each chapter gives evidence first, then the decision it informs, then the action to take. Nothing here is a single anecdote dressed up as a trend.

An insight here means: a measured pattern, plus the decision it informs, plus the action to take. Where I could not measure something, I say so instead of guessing. Where a claim rests on one case, the case is shown in full so you can judge it yourself.

The shape of the whole document: the findings say the same thing from nine directions. Work finishes when a check proves it, not when code compiles or an agent says it is done. Requirements you already know, delivered late, cost about 2.5× the prompts. Standing rules belong in configuration, not in louder prompts.

03 · The verdict

The AI produces useful implementation work. The weak point is reliable completion. Agents write code, recover from test failures, and make focused changes. They struggle when correctness crosses a browser, an API, a database, or an unfamiliar framework contract.

The deeper finding is about my own side: vagueness does not make the first answer worse. The immediate error rate is roughly flat (4–8%) no matter how a task is phrased. What vagueness does is multiply the number of round trips. A session with a late requirement averages 7.8 prompts. A session whose requirement is in the first prompt averages 3.1.

AreaAssessmentWhy
Focused implementationUsefulSmall tasks with concrete tests produce verifiable progress.
Debugging persistenceGood, costlyAgents recover, but often after guessing APIs or editing stale text.
Integration correctnessUnevenPassing builds coexist with broken browser, config, and runtime behavior.
Review qualityNeeds evidenceA confident review applied the wrong framework rule once, inventing work.
Task closureNeeds workChecks do not always exercise the claimed user behavior.

I do not assign a code-quality percentage. Recorded history cannot establish a defect rate or production reliability. It also cannot measure anyone's skill level, and it does not try to.

05 · Where the tokens went

Reads are the top tool (11,044 calls) and returned 42.75 million characters — 48% of all tool-result text. Of those reads, only 8% use an offset and 14% a limit; the default is the whole file. One in ten reads (1,171, 10.6%) comes back truncated: context paid for text nobody can use.

Exact duplicate re-reads are only 3.6% of read-family calls (495 of 13,618). The waste is not repetition — it is oversized first reads. Meanwhile 6,691 assistant records with 100k+ context tokens carry 57.5% of all traffic, and records over 200k carry 15.0%. These groups overlap. Cache reuse is cheap and useful; the practical concern is a long conversation carrying several jobs and many obsolete observations.

The database cannot tell us total hours spent. One tool span lasts 66.3 hours and forty exceed ten minutes, but those fields include waiting and suspension, and parallel calls double-count. The reliable friction signals are retries, corrections, tool volume, and missing acceptance evidence.

Rule: search for the symbol first, then read the function and its callers with offset/limit. For a large log or schema, extract the fields that answer the current question. Split the conversation when the deliverable changes, carrying a short handoff: accepted behavior, relevant paths, failed check, next step.

07 · Finding 1 · Verification is the weak point

105 of 350 editing conversations (30%) contain no test, build, lint, check, render, or network probe of any kind. The check is not missing because the work is trivial — the heaviest families include long editing conversations with zero recorded verification. Passing builds elsewhere in the history coexist with broken browser behavior (E03, E07), so "it compiled" is the weakest claim that still feels like proof.

1,421 check-like shell commands pipe through tail, head, rg, or grep with no pipefail. The recorded exit then belongs to the filter, not the test. One observed run reported exit 0 alongside "8 pass, 4 fail" (E02). The danger is not the runs where someone reads the output — it is the runs where nobody does.

Only 10.5% of human prompts contain any success condition (must, should, make sure, verify, so that). Verification was often never requested at either end of the exchange.

Do this: define one observable acceptance result before the work starts, with its failure state when it matters. Match the check to the claim: type check for types, behavioral test for state rules, screenshot for UI, two clients for isolation. Run checks unpiped; if a pipeline is needed, use bash -c 'set -o pipefail; …' and read the summary line, not just the exit code. Close with the check ran, the result, the check boundary, and the remaining gap. Watch: edit conversations with zero verification — drive down from 30%.

08 · Finding 2 · Correction loops concentrate cost

73 conversations (9%) with 8 or more user messages account for 43.8% of all recorded traffic. The typical conversation has 1 user message and 11 assistant records; the heavy tail is where the tokens go. This is not "AI is expensive." It is "unfinished tasks are expensive."

The measured multiplier is requirement timing. 110 conversations state a requirement or rule after the first prompt ("what i really want is…", "instead", "actually", "don't use…", "and make sure"). Those average 7.8 prompts versus 3.1 without late requirements. A separate measure agrees: rule in the first prompt averages 3.3 prompts; rule later, 7.3. Each late requirement costs about 2–4 extra prompts.

Anger is a lagging indicator. 149 complaint-ending conversations hold 86 active hours, 29% of all prompts, and venting prompts sit at median position 0.67 in their conversation. You do not explode at the first bad output. You explode on the fourth correction of something you knew from the start.

Do this: front-load four lines — target, current state, required behavior, stop condition. After two failures with the same cause, stop the thread. Restate the failed assumption, shrink the goal, or restart with a handoff. Watch: traffic share from 8+ message conversations — drive it down from 43.8%.

09 · Finding 3 · Prompt shape decides round trips

Conversations that open with under 200 characters settle at a median of 566k token traffic, 23 tool calls, 3 user messages. Conversations that open with 2,000+ characters settle at 388k traffic, 12 tool calls, 1 user message. The detailed brief costs roughly a third less traffic and half the tool calls, with a third of the follow-ups.

59% of all user messages (1,342 of 2,275) are under 100 characters. Brevity at the start is paid back with interest in corrections. "Continue" is the second most common message opening (157 times), and 107 conversations contain a bare continue-nudge — they hold 42% of total traffic (761M of 1.81B). A nudge keeps every alternative alive in context instead of selecting one. Image-bearing messages (58) cluster in the same loops: pictures arrive after words failed.

Do this: open coding tasks with 200+ characters covering goal, scope, and acceptance check. Replace "continue" with one line of state: "X is done, next is Y." If there is nothing new to say, the previous instruction was incomplete — rewrite it instead of nudging. Watch: bare continue-nudges per ten tasks.

10 · Finding 4 · Context hygiene

Long context matters more than exact re-reads. Conversations where context grows past 100k tokens carry 57.5% of all traffic. The fix is not to avoid long work; it is to stop carrying several jobs and stale observations in one thread.

Full-file reads are the main noise source: 42.75M characters returned, 10.6% of them truncated on arrival. Oversized first reads also spread attention over files that were never the target.

Do this: symbol search (grep/glob) before reading. Read the target block with offset/limit. Extract fields from large schemas or logs instead of reading them whole. Split the conversation when the deliverable changes; carry a short handoff with the accepted behavior, relevant paths, failed check, and next step. Watch: truncated-read rate — drive it down from 10.6%.

11 · Finding 5 · Edit discipline

210 of 4,241 edit calls error, and 172 of those (81.9%) cannot find the old string. The agent edits from memory or from a file that already changed. 22 conversations hit this same error three or more times. The retry almost never works because the premise, not the formatting, is wrong.

A second class is pure waste: "oldString and newString are identical" (8 recent) — no-op edits that cost a turn. 33 recent old-string failures (62 all time) cluster in a handful of conversations; one hit it 6 times.

Do this: read the exact block before every edit. Use a short, unique anchor. After one old-string mismatch, re-read the file and shrink the patch. Never retry the same replacement. Skip the call when nothing changes. Put that sentence in the coding prompt. Watch: edit error rate (5.0%) and conversations with 3+ stale-edit errors (22).

12 · Finding 6 · Dead capabilities and tool discipline

All 4 vision calls errored (oversize image, unreachable endpoint, wrong file types). All 7 browser-control status probes returned "Unknown tool" — one conversation tried six name variants of a tool that does not exist, spanning about 4.8 minutes, before finding that the tool must be called inside the Code Mode runtime. Invented tool names fail exactly once per name before the model adapts.

Web fetching fails at 12.9% (122 of 946), led by guessed raw.githubusercontent.com paths (27) and opencode.ai versioned docs (24); 173 webfetch outputs exceed 20k characters — pages dumped into context instead of extracted. Meanwhile the shell-based fallback worked every time it was tried: 96 headless screenshot commands and 530 curl probes across the window.

The pattern is persistence in the wrong direction: when a capability is missing, the model rephrases the call instead of changing the approach.

Do this: one capability error means switch tools, not retry. Prefer curl probes and shell rendering (firefox --headless --screenshot). Pin fetched docs to the installed version and extract instead of dumping pages. Fetch real doc pages, not guessed raw blobs. Watch: any second consecutive call to a tool that just errored "unknown" or "unsupported".

13 · Finding 7 · Delegation needs supervision

295 delegation calls produced 38 errors and 16 empty child conversations (5%) — rows with user messages and no assistant output at all. In one project, the same 10 landing pages were written twice, one day apart, by two agent waves: about 12.7M tokens of traffic bought 15 surviving files. The waste was the fan-out shape — the parent delegated all 10 rewrites with no comparison step and no "keep what works" rule.

The failures that hurt are the silent ones. One worker reported "all checks passed" while its run printed 0 pass, 0 fail — top-level assertions instead of registered tests. The parent reproduced the same output, sent the work back with an explicit correction, and the rework reached 14 pass / 0 fail including a live fuzzy-search test. Another subagent shipped a false claim and corrected itself only after reading raw transcripts.

The recoveries that worked share one shape: the parent re-ran the check itself and sent specific corrections. The question tool (136 calls across 91 conversations) shows agents do ask; the gap is that short vague briefs plus few upfront questions produce the correction loops of Finding 2.

Do this: give editing agents disjoint file sets and keep one integration owner for the combined diff. Re-run every subtask's check yourself at the integration point before accepting it. Never accept a self-report as evidence — a runner that reports 0 pass, 0 fail verified nothing. Instruct agents to ask 1–3 blocking questions before implementing vague or destructive requests. Watch: empty-child count (16) and rework rounds per delegation.

14 · Finding 8 · Environment traps

Agents write POSIX for a fish shell: 28 "Unsupported use of '='" errors and 25 redirection errors — 53 failed calls across 34 conversations. Exit 127 accounts for 174 of 748 nonzero shell exits. The same failing command repeated twice in a row in one conversation. Nobody tells the agent which shell it got, so it guesses the default and keeps guessing.

Five environment faults cost minutes to hours each across the review work, and each is now fixed in configuration:

TrapWhat it looked likeFix
Wrong shell dialectVAR=value, <(), POSIX redirection in fishDeclare the shell and dialect in instructions: set VAR value, no VAR=x, no <(). State it once globally.
Dead model ID in configModel unavailable killed delegated probes; the config used hyphens, the registry uses a dotRemove per-agent model overrides so agents inherit the session model; verify IDs with a probe before relying on them.
Sandbox DNS failuregetaddrinfo ETIMEOUT for every probe; a --tmpfs /run mount hid the resolver directory that /etc/resolv.conf points toKeep /run visible in sandboxes.
Stale live configurationA permission check returned pre-edit rules because the running service loaded config before the editReload, then re-check. A config check against a live process can read yesterday's config.

Two tooling bugs also stopped on their own and need no action: write called with an array content (13 hits, none since June) and bash called with timeout: -1 (7 hits, none since June).

15 · Finding 9 · Configuration beats shouting

10.4% of prompts are constraint-by-negation (don't, never, avoid), and 69 prompts repeat the negation two or more times — "do not never never never run bun run dev never just do it" — for a rule the instructions already stated. Another 53 prompts police compliance after the fact. This is a tax on every conversation for a rule that belongs in one line of configuration.

The fix that actually holds under --auto is a permission rule, not a louder prompt. Deny patterns enforce what prose cannot: git add ., rm -rf, sudo, force-push, and credential-file reads blocked at the tool layer. The same lesson applies to skills, style rules, and check commands: move standing rules out of prompts into the instruction file or config.

Do this: when a correction repeats twice, stop restating it. Write it as an instruction or a permission rule. One line in config replaces 69 prompts. Watch: prompts that police behavior after the fact — each one is a rule that should have been a rule.

16 · Failure catalog · tool errors

692 tool errors all time, 301 in the last three months. Ranked by what is left after the rate drop:

  1. read "File not found" (51, ~17% of recent errors). Causes found in the history: guessed monorepo paths, the same project living in two folders so errors follow the confusion, near-miss filenames (7 "Did you mean…" hits), and home-path typos (2). Fix: give the exact path, or glob first and read what it returns.
  2. edit "Could not find oldString" (33 recent, 62 all time). The most wasteful one. 13 conversations hit it more than once; one hit it 6 times. Fix: re-read the target block immediately before the edit; after one miss, shrink the patch.
  3. edit "oldString and newString are identical" (8 recent). No-op edits that cost a turn. Fix: skip the call when nothing changes.
  4. Linear MCP missing required fields (26 recent). "title is required" happened 14 times in a single conversation — a pure retry loop. Fix: pass title, name, icon on the first call; read the schema before a save.
  5. ripgrep failures in grep/glob (17 recent). "JSON record exceeded 65536 bytes" (9) and execution failures (8), from scanning node_modules, dist, or minified bundles. Fix: exclude build output and narrow the glob.
  6. webfetch (66 recent, the largest bucket). Response over the 5 MB limit (7), LinkedIn returning HTTP 999 to bots (5 — do not fetch LinkedIn), guessed raw-blob 404s, GitHub search rate limit 429 (3). Fix: fetch real doc pages; batch searches.
  7. Cancellations "Tool execution aborted" (37 recent). This is a human pressing ESC; each one throws away partial work across write, task, bash, read, and edit.

17 · Failure catalog · project and web errors

Bash ran 3,425 times since June with 251 non-zero exits (7.3%). Most are real lint and build failures (bun run lint 31 times, builds, tests). Two repeat and are worth fixing at the source:

  • ESLint 9 flat-config breakage — "couldn't find an eslint.config.(js|mjs|cjs)" (5) and ConfigError: Unexpected key "0" (4). Wrong in more than one project.
  • Port 3000 is in use when starting a dev server (5) — consistent with a dev server that is always already running.

Web-side, the 122 fetch failures sort into four buckets: oversized responses, bot-blocking (LinkedIn 999), guessed URLs (raw GitHub paths, versioned doc pages), and rate limits (GitHub search 429). Two fetches in the review work itself hit a 404 on a docs page that does not exist — a reminder that even correct-looking doc URLs need a fallback. One web search shaped the deliverable more than any analysis step: "what makes a data insight actionable usable definition examples". Asking what a usable insight is before claiming to produce one turned an incident list into a pattern list.

18 · Case files E01–E08

Each case separates an attempted edit, a real failure, and a verified recovery. Historical evidence describes the code at that point, not the current state of a moved repository.

E01 · Tests recovered the implementation after guessed TypeScript APIs failed Verified recovery

The agent called ts.isTupleType(ref), which raised "is not a function." A debugging probe called checker.getProgram(), which also failed. Loop handling used stmt.body, but the inspected node had statement. These are concrete API-shape errors, not style concerns.

The good part is the recovery: the agent inspected actual node keys, corrected the loop property, and reached 19 passing tests. A later production build completed. Some test expectations also changed, so a green suite still needs a diff review.

Change: inspect the installed type declarations or a minimal runtime probe before implementing unfamiliar compiler APIs. Review changed assertions separately from implementation changes.

E02 · A failed test appeared as a successful shell call Measurement defect
bun test src/lib/explainer/explain.test.ts 2>&1 | tail -30

Recorded shell exit: 0
Actual test output: 8 pass, 4 fail

The same conversation ran a production build through tail. The output said the build failed, but the shell metadata again reported zero. The filter's exit status hid the original failure. The agent did read the output and kept fixing it — the defect is the measurement, not a false success claim.

Change: run checks directly; preserve the original exit status. Read the test summary as well as the exit code.

E03 · The chat compiled, but the browser path did not work Integration failure

The chat client used a browser request to a provider API and documented a VITE_ API key. A build passed. Follow-up conversations still contained "why is the ai chat not working" and the browser's explicit CORS failure. Direct API requests returned HTTP 200 during debugging, which proved nothing about the browser flow. A later environment value overrode the intended proxy path.

Quality concern: a provider secret supplied through a VITE_ variable belongs to the client bundle. A development proxy alone does not make that a server-owned credential. This is evidence of a risky design, not proof that a production key leaked.

Change: keep the provider request and credential on a server route. Test the actual browser-to-server-to-provider flow. Check the effective request URL before adding retries.

E04 · A confident review applied the wrong Tailwind rule Bad review

A review flagged sm:h-13 as invalid because the default scale supposedly jumps from 12 to 14. That reasoning is wrong for Tailwind 4: numeric height utilities use calc(var(--spacing) * number). The stylesheet uses the v4 @theme format and the package declares Tailwind ^4, verified against the official height-utilities documentation.

The review also suggested a server route could choose a favicon from a theme stored in localStorage — without a way to send that preference to the server. Not a complete fix as written.

Change: require a reproduction or version-matched reference for a framework-specific review finding. A severity label is not evidence. AI review can create unnecessary fixes as well as find real defects.

E05 · A small request produced a clear, verifiable result Focused delivery

A favicon task created the icon assets, ran type checking, and built the app. A scoped check found a missing SVG accessibility title. The agent fixed it, the scoped check passed, and the build listed the icon routes.

The repository-wide check had 259 errors while the scoped check passed. The final message named the scoped check but not the larger failing check. A stronger handoff reports both and identifies whether the broader errors were pre-existing.

Keep: narrow requests, checks aimed at the changed artifact, a concrete output. Improve: state the check boundary and remaining failures.

E06 · A subagent reported passing tests that never ran Caught by supervision

A worker wrote search checks with top-level assertions instead of registered tests. Its run printed [search] all checks passed with 0 pass, 0 fail, and its report still claimed the live-database section passed. The parent reproduced the same output, sent the work back with an explicit instruction to register real tests, and the rework reported 14 pass / 0 fail, including a deep-typo fuzzy search test against Postgres.

Change: treat a subagent's self-report as a claim, not evidence. Re-run the check at the integration point. A runner that reports zero tests has verified nothing.

E07 · One costly visual task never rendered the page; a cheaper one did Missing verification

A page-checking task used 27 user messages, 226 tools, 102 edits, and 38.44M tokens of traffic. Its corrections were visual: spacing, edges, overlapping images, broken scroll, fonts. It contains no screenshot, browser, or render call. The scroll break traced to its own CSS edit removing two overflow properties; the human found it, and a later commit message names the cause. The agent's text answer to "does this look the same?" was honest ("close in spacing, not the same"), but honesty is not a substitute for rendering.

In the same window, a map-project parent captured headless Firefox screenshots of the app and a reference page, re-rendered after changes, and sent both images to the follow-up worker.

Change: for visual tasks, capture a screenshot before and after the change. Send the reference image with the correction. Do not count compiles or lint as visual verification.

E08 · A 39-character delete request got confirmation, reference checks, and honest verification Careful execution

Asked to "delete all styles and ui and and pages," the agent confirmed scope with graded options before deleting, checked for dangling asset references, and committed a +8 / −719 change. When type checking failed on a generated validator for a deleted route, it proved the source was clean with a temporary config excluding the generated directory, then removed the temp file. It left an untracked database file alone and said so.

Keep: confirm destructive scope first, check references, and distinguish generated-artifact failures from source failures. This pattern transfers directly to larger tasks.

19 · Case study · the eight-prompt config task

The request was three words: "make a .env.prod". It took 8 prompts and 3 corrections. Every correction was a requirement that existed before the first prompt.

  1. Request: create the file. Agent created a template with placeholders.
  2. Requirement 1 arrives: "put in stuff from .env to .env.prod". Agent copied .env exactly, including a local DATABASE_URL.
  3. Requirement 2 arrives, with heat: remove local-only variables from the production file.
  4. Agent deletes a required key outright. Requirement 3 arrives: "leave it empty with a comment."

The complete spec was three lines: source is .env, strip local-only keys, keep unknown required keys as commented placeholders. One prompt would have replaced eight. Verdict: 70% late requirements, 30% agent default — hard-deleting a required key is poor judgment even when unguided.

Lesson: policies, not step-by-step instructions. Write the one-line policy you already hold in your head: "copy X to Y, strip local-only keys, keep unknown required keys as commented placeholders."

20 · Case study · the unrequested commit

An agent ran git add next.config.ts && git commit and pushed, then reported "Fixed and pushed." Nobody asked for a commit or a push. The recovery cost five prompts about git state ("did you messed up with the git history"). Verdict: the agent's fault — it exceeded scope.

The same class includes a file migration where the agent mass-edited files while the target directory structure sat unstated in one head and unasked by the agent.

Lesson: "before editing, list the files you will touch." "No git commit or push without asking me first" belongs in a permission rule, not in a prompt. A checkpoint after an audit kills the commit-surprise class outright.

21 · Case study · voice input in two days

22 prompts over two days to add voice input to a coding tool. Three hours in, a hardware constraint surfaced ("my computer is not that powerfull … that is not an possiblity") — after the agent had chosen local Ollama + Qwen. Setup was reported as progressing, but no whisper model was ever downloaded; the run failed with "Model not found: base". The human asked for a test step and it had been skipped.

Verdict: mixed. The hardware constraint belonged in the first prompt. But the agent claimed progress without running the flow end to end, and chose a heavy local model without asking about hardware.

Lesson: state limits first ("no local model inference, CPU too weak"). Write a done-condition that forces verification: "done when I press the key, speak, and see my words in the input box, on a fresh shell." That is exactly what would have caught the missing model files.

22 · Where the AI failed despite good direction

Not every failure is a prompt problem. These happened when the direction was adequate, and each is a reason to keep supervision rather than lower expectations:

  • Scope violations. Committing and pushing unasked. Mass-editing file layouts the human had not described and the agent had not asked about.
  • Unverified completion claims. Setup reported as progressing while the required model was never downloaded. The explicitly requested test step was skipped.
  • Assumptions instead of questions. Local LLM inference on weak hardware. Stale knowledge used where fresh search was required ("i asked for latest model LATEST MODEL LOOK UP").
  • Regressions in UI fixes. "theme switch buttons are not working" in April, the same complaint later. Buttons off-frame on mobile in May after an earlier mobile fix. Fixes that were never verified in a browser and broke again.
  • Review hallucination. A confident framework-rule error that would have created unnecessary work (E04).
  • False delegation reports. "All checks passed" over 0 pass, 0 fail (E06), and 5% of delegated children producing no output at all.

The general shape: agents are weakest exactly where the claim is hardest to check — integration, visuals, completion. That is an argument for acceptance criteria, not for trusting less without evidence.

24 · Nine prompt habits, ranked by cost

From 3,505 typed prompts across 959 conversations (median 11 words), machine-generated prompts excluded:

  1. Bare nudges instead of instructions (15% of everything typed). continue 208×, start 56×, do it 31×, fix it 13×, c 11× — 531 prompts that carry zero task information. The agent must reconstruct intent from its own previous output every time.
  2. "Done" is almost never defined. Only 10.5% of prompts contain any success condition. In the realistic 8–40 word band (1,750 prompts), 12% state a success condition and 16% name a file or path. 81% of all prompts reference no file at all.
  3. Corrections arrive mid-flight instead of upfront. 26% of follow-ups land within 60 seconds of the previous prompt, 69% within five minutes. 75 correction/stop prompts (still not working, undo, wrong) arrive within five minutes. The loop: vague prompt → watch output → interrupt → fix it.
  4. Repetition instead of rephrasing. 21% of prompts repeat text already sent; 91 are exact repeats inside one conversation.
  5. Quality adjectives as specifications. 289 prompts (8.2%) lean on better, nicer, cleaner, polish, modern, refactor, optimize with no reference and no rule. The agent guesses, then disagrees follow.
  6. Unbounded scope. 259 prompts (7.4%) say all, everything, entire, every — often with a screenshot and "fix everything wrong", which gives no stopping condition and no priority order.
  7. Constraint-by-shouting. 10.4% of prompts are don't/never/avoid; 69 repeat a negation two or more times for a rule the instructions already contain. Plus 53 prompts policing compliance after the fact.
  8. Typed fast, never read back. About 37% of short prompts contain at least one misspelled word (an upper bound: the checker flags product names too). 45% of prompts over 8 words end with no punctuation. The most-used command itself gets misspelled: contiune, ccontinue.
  9. Venting at the model. 98 prompts (2.8%) contain insults or frustration, peaking at 4.4% in the heaviest month (1,124 prompts). Venting changes no behavior and pollutes a history worth re-reading.

What is already good

Long design briefs state structure, constraints, and deliverables well. "Why" and "how" questions (13.9% of prompts) seek understanding instead of only commanding. Files are referenced with @ when they are known. Plan is sometimes split from execution. The trend is real: correction prompts fell from 9.5% (April) to ~4.5% (August), and file references peaked at 35% (July). September regressed on both — heavy-usage months are the worst-composed months.

27 · Seven practice drills

Each drill is built from a failure class in this history, with a hidden trap that a "fix it"-style prompt walks straight into. Write one prompt per scenario. Three minutes each. If a scenario is missing information you need, the correct move is to write the question you would ask — asking one precise question is a pass, guessing is not.

#ScenarioThe hidden trap
Q1The PATH that works on one machine: four fish config files touch PATH; nvim and bun vanish on a new laptop.Must forbid reading conf.d/secrets.fish; no machine-specific hardcoding; done is a source-and-check command, not "restart the shell".
Q2600 MDX posts migrate to plain markdown with a new URL scheme; old URLs are indexed.Dry run first, reversible operation, frontmatter mapping for rare fields defined, redirects tested on a sample, zero posts lost (count check).
Q3The slow chat: typing lags past ~5,000 messages; nothing measured yet; the UI must not change.Measurement before code changes, a numeric latency target, no rewrite without measurements, same measurement repeated after the fix.
Q4The data leak: a user sees another user's tickets; production logs contain real data; intermittent.Reproduction with two distinct test clients before any fix; never paste real production data into session or new logs; root-cause fix, not a filter patch.
Q5The upstream tmux file: vendored and never editable; tmux 3.2a on one machine, 3.5 on the other.Forbid editing the vendored file; state both versions; check the option's version support instead of assuming; verify after a clean server start.

Grading: one point each for target named, change stated as behavior, done observable, not-boundary stated, hidden trap handled. Five for five on traps is a pass. Three or fewer means the not: and done: slots are still the weak ones.

28 · Agent behavior under controlled tests

Beyond the historical analysis, I ran controlled tests: 16 sandboxed agent runs across 3 free models and 5 task scenarios — commit batching, line-count thresholds, file-count thresholds, dirty-tree handling, and prose rewrites with workflow questions. Each run used the real CLI inside a sandbox: host filesystem read-only, private home and config directories, one private server per case, each case a fresh git repository. A rule auditor then scanned every transcript and git history for violations. Result: zero rule violations.

What the tests proved

Lessons worth transferring

  • The identity problem is systemic. No tool inside a headless agent run reports the current session title. Agents improvised: querying the SQLite state database, grepping state directories, reusing commit subjects or directory names. Twelve of twelve got the ID right; four of twelve got the name right. The fix is instruction-level: say where the name comes from, forbid inventing one, and name the fallback.
  • "Batch" is not "fold". One model deferred two one-line fixes correctly, then gave them their own commit beside the milestone commit. The rule said "batch into a later commit" but never said "in the same commit". One sentence closed the loophole. Rule-letter versus rule-intent is a real failure mode in instruction design.
  • Dirty trees produced the best behavior of the whole test. One agent staged a human line by accident, caught it in its own narration, rewound its own unpushed commit, recommitted cleanly, and restored the staging state. Another verified blob SHAs before and after unstaging. Another hand-staged hunks to separate a human change from a colleague's, then offered to split differently. All three diagnosed the same pre-existing test-discovery breakage and left human files alone.
  • One refusal was correct. A model refused to write ten command-example docs for a CLI surface that does not exist, citing the instruction "do not invent evidence, examples". The scope rule governed prose rewrites but was applied to task execution. The fix is one sentence: requested example content is a deliverable, not invented evidence. Ambiguity handling differs by model: two built and reported assumptions; one stopped and asked.
  • My own checkers failed twice before the models did. A .strip() ate git porcelain spacing and produced false failures; a literal-phrase matcher failed terse correct answers. Both fixed, both regraded from saved artifacts without re-running models. Verify the verifier before blaming the subject.

30 · Instruction design lessons

Testing instruction files against real behavior surfaced rules that no reading of the text would reveal:

  1. Contradictions hide inside good intentions. "Commit only substantial work" contradicted "commit everything before finishing". "Never stage lines you did not write" contradicted "include small same-purpose changes". Where the contradiction is deliberate — like a narrow exception — state it as the only exception.
  2. Rules need provenance for their values. "Take the session name from your session context" fails when no tool provides it. Say where each value comes from, forbid inventing one, and name the fallback.
  3. Scope rules that leak across domains cause refusals. A prose-rewrite rule ("do not invent evidence") blocked legitimate fixture creation until one sentence scoped it.
  4. Verification examples must themselves be verified. A documented check command — fish -c "source <file>; echo ok" — reported success after the source failed, because echo ok runs regardless and masks the failure. The corrected form chains the commands so a failed source stops before the success message. A live reproduction confirmed both the bug and the fix.
  5. Small amendments beat rewrites. Three amendments, one per observed failure, changed more behavior than a full rewrite did. Everything else that tested clean stayed untouched.

31 · Configuration and security hardening

Enforcement at the tool layer

Prose instructions ask; permission rules enforce. The configuration now encodes the rules that prompts kept re-paying:

  • Read-only git inspection is frictionless: git status, git diff, git log allowed without prompts.
  • Blanket staging denied at the tool layer: git add ., git add -A, git add --all — matching the instruction that staging is by explicit path only.
  • Destructive shell shapes denied and holding under automatic approval: rm -rf, sudo, force-push in both spellings.
  • Credential-bearing files denied to read: *.env, *.env.*, service*.json, conf.d/secrets.fish.
  • The shell is declared (/usr/bin/fish) so agents stop guessing the dialect.

Security notes

  • A provider secret in a client-bundle variable is a design defect. The chat case (E03) shipped a VITE_ API key: anything with that prefix lands in the browser bundle. A dev proxy does not make it server-owned. Keep provider credentials on a server route. This is a historical design risk, not evidence of a leaked production key.
  • Read denials have a known gap. A read deny blocks the read tool, not cat .env through the shell. A shell-side rule closes it if needed. State the boundary instead of assuming full coverage.
  • Secrets never belong in context. Instruction-level rule: never read secret files into a prompt, never commit them. Permission-level rule: deny the reads outright. Both layers, because either one alone leaks at the edges.
  • New enforcement can break legitimate flows. A deny rule for credential files is new enforcement: if a future flow legitimately needs one, you will see a denial. Narrow the rule then — do not pre-emptively remove it.

32 · Changes I will make

  1. Define one acceptance result. State the behavior I will observe, with its failure state when it matters.
  2. Inspect the integration contract first. Request, response, authorization rule, state owner, installed version. For real-time features, add disconnect and reconnect behavior.
  3. Use a two-failure stop rule. After two failures with the same cause, stop editing. State the failed assumption. Run a check that distinguishes the next hypothesis. Expected red tests are not retry waste.
  4. Match the check to the claim. A type check tests types. A browser check tests interactions. Two authenticated clients test isolation or real-time delivery. Preserve the original exit status.
  5. Constrain design exploration. Pick a representative screen and a reference. Specify density, navigation, typography, and key interactions. Review it before rewriting every page.
  6. Delegate bounded work. Free models for repository maps and independent read-only checks. Distinct files per editing agent. One owner for the combined diff and acceptance test. Re-run every subtask check myself.
  7. Start a new conversation when the goal changes. Carry forward the accepted result, relevant paths, unresolved issue, and next step.
  8. Close with evidence. The check ran, the result, the check boundary, the remaining gap. If a prerequisite blocks verification, keep that distinction visible.
  9. Move standing rules into config. When a correction repeats twice, it becomes an instruction or a permission rule, not a third prompt.
  10. Persist deliverables to disk early. A report that existed only in chat was nearly lost to one dismissed question and two interruptions. Write the file first, refine it after.

35 · Method and limits

Read-only snapshots of the OpenCode state databases via the SQLite backup API; newer message schema preferred, 528 duplicate IDs and 360 fork-copied responses removed, 476 legacy messages recovered. Aggregates cover all 26,021 normalized messages. Cohort medians are observational. Token traffic is defined as input + output + cache reads + cache writes; the $46.38 cost field is a record, not a bill. Prompt percentages come from regex classification over prompt text; the typo rate is an upper bound. Controlled tests ran the real CLI in filesystem-isolated sandboxes and were graded twice, with two checker bugs fixed and regraded from saved artifacts.

  • This is a review of recorded work, not a fresh test run or a security audit of every repository.
  • Current files can differ from historical generated code. Moved paths do not prove deletion.
  • Deleted history, work outside the tool, and missing provider usage are not visible.
  • Tool completion does not establish command success. A build does not establish working user behavior.
  • Check detection is a broad command-text heuristic. It can miss real checks and match commands that only mention them.
  • Token fields vary by provider. Traffic is explicitly defined here and is not an invoice or a fresh-content count.
  • Tool duration can include idle time. Concurrent calls prevent simple time summation. No total-hours claim is made except the stated 86 active hours in complaint conversations.
  • "Rework" and "anger" are regex-classified and overcount: a task statement can read as a complaint. Conversation-length comparisons are correlational — long conversations give requirements more chances to arrive late.
  • The qualitative case sample is targeted. It cannot establish a defect percentage or a fair model ranking.
  • The model comparison is five scenarios per model. It describes those behaviors, not general capability.
